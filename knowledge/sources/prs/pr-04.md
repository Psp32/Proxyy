# Overview

Improved error handling and developer experience in Layr by replacing generic error messages with user-friendly, context-aware troubleshooting guidance.

The contribution updated multiple error classes and application modules so that errors provide actionable information about what went wrong, how to resolve the problem, and where to find additional documentation or support.

The implementation also introduced provider-specific behavior for Gemini and Groq, ensuring that users receive different guidance depending on the AI provider being used.

# Problem

Layr's existing error messages did not provide enough context for users to understand what went wrong or how to resolve configuration and provider-related problems.

Generic errors could leave users unsure about:

- Which configuration was missing.
- Whether an API key was required.
- How to configure a specific AI provider.
- Whether an external AI service was unavailable.
- Where to find setup documentation.
- Where to check service status.
- Where to report or investigate an issue.

The contribution focused on turning these errors into actionable troubleshooting experiences.

# Key Changes & Implementation

## Error Classes

Updated the following error types:

- `APIKeyMissingError`
- `AIServiceError`
- `UnsupportedProviderError`

The errors were enhanced to provide provider-specific and context-aware guidance.

## Gemini Support

For Gemini-related configuration errors:

- Added API key setup instructions.
- Provided documentation links for configuring Gemini.
- Clarified what users need to do when a Gemini API key is missing.
- Directed users toward relevant setup documentation.

## Groq Support

For Groq-related errors:

- Clarified that Layr uses a secure proxy.
- Communicated that users do not need to provide their own Groq API key.
- Reduced potential confusion around provider authentication requirements.

## Context-Aware Troubleshooting

Error messages were expanded to include actionable troubleshooting steps.

Depending on the error, users can receive:

- Setup instructions.
- Documentation links.
- API status-page links.
- GitHub issue links.
- Provider-specific guidance.
- Information about whether user configuration is required.

## Provider Validation

Fixed provider validation so that the application properly distinguishes between providers with different configuration requirements.

This prevents the application from incorrectly treating all providers as requiring the same authentication or setup process.

## Module-Level Improvements

Improved error handling across multiple areas of Layr, including:

- Planner module.
- Provider modules.
- Extension modules.

# UX / Developer Experience Improvements

The primary goal was to make errors useful rather than merely descriptive.

Instead of an error simply stating that something failed, the new approach gives users enough context to take the next step.

For example, a provider configuration error can communicate:

1. What went wrong.
2. Which provider is involved.
3. Whether an API key is required.
4. How to configure the provider.
5. Where to find official documentation.
6. Where to check service availability if the problem is external.

# Impact

This contribution improved Layr's developer experience by making configuration and provider-related failures easier to understand and resolve.

The changes reduce ambiguity around AI provider configuration and give users direct paths toward documentation, service-status information, and issue tracking.
