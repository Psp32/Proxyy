# Overview

Recovered and substantially expanded the Turtle project into a multi-computer orchestration platform.

Turtle explores a different way of interacting with multiple computers: instead of manually connecting to individual machines, opening separate terminals, and repeatedly executing commands, users can describe a desired workflow in natural language.

The system interprets the request, breaks it into tasks, plans the execution, distributes work across connected machines, and keeps execution synchronized through a centralized interface.

This recovery branch introduced a substantial amount of frontend, mobile, backend, orchestration, planning, synchronization, and reliability functionality.

# Problem

Managing multiple computers independently creates repetitive and fragmented workflows.

Typical problems include:

- Connecting to machines individually.
- Opening and managing multiple terminal sessions.
- Repeating the same commands across different machines.
- Losing visibility into what each machine is currently doing.
- Managing long-running tasks across multiple systems.
- Coordinating execution state between machines.
- Recovering from connection or execution failures.

Turtle was designed to treat multiple computers as one coordinated workspace.

# Product Concept

Turtle allows users to give a high-level command in plain English rather than manually orchestrating individual computers.

A typical workflow is:

1. User provides a command or desired outcome.
2. The system interprets the request.
3. The request is divided into individual tasks.
4. Tasks are planned and routed to appropriate machines.
5. Connected machines execute their assigned tasks.
6. Execution state is reported back to the centralized interface.
7. The user can monitor the overall workflow from one workspace.

The core product idea is to make managing a fleet of computers feel similar to controlling a single computer.

- Multiple navigation pages

The frontend was subsequently refactored from the initial mobile-oriented implementation toward a broader frontend architecture.

## Navigation

Added multiple navigation pages to organize the application and provide different views into the orchestration workflow.

## Fleet Pipeline

Introduced functionality for managing a fleet of connected machines and coordinating execution across them.

The fleet pipeline provides the foundation for:

- Task distribution.
- Machine coordination.
- Execution tracking.
- Centralized workflow state.

## Planner

Added planning functionality that can transform a high-level user request into a structured execution plan.

The server introduced a `/plan` endpoint to support this workflow.

The planner allows Turtle to move from a natural-language request toward executable tasks.

## Synthesis

Added a synthesis workflow for combining or processing results from distributed execution.

The server introduced a `/synthesize` endpoint.

The mobile/client side also gained decomposition and synthesis functionality.

## Gemini Hardening

Added hardening around Gemini-powered functionality.

The implementation included reliability-oriented handling around AI-powered planning and synthesis operations.

## Retries & Reconnection

Added reliability mechanisms for distributed execution, including:

- Retry handling.
- Reconnection helper functionality.
- Timeout handling.
- Rate-limit handling.

These mechanisms help the system remain usable when individual services or connections fail temporarily.

## Planned Sessions

Added support for planned sessions to represent orchestrated workflows and their execution lifecycle.

## State Management

Introduced reducer-based state handling and logging to help track orchestration state.

This supports centralized visibility into what is:

- Planned.
- Running.
- Completed.
- Failed.
- Awaiting attention.

## Error Handling

Added an `ErrorBoundary` on the frontend and improved error-related handling throughout the workflow.

This provides a more resilient user experience when frontend or orchestration operations fail.

## Planner Dispatch

Added frontend planner dispatch functionality to connect the user interface with the planning workflow.

This allows a user request to move from the frontend into the orchestration/planning pipeline.

## Testing

# Architecture

The recovery work spans multiple layers of the Turtle system.

## Client / Mobile

Responsible for:

- User interaction.
- Workflow decomposition.
- Synthesis.
- Reconnection.
- Progress visibility.
- Orchestration controls.

## Frontend

Responsible for:

- Planner dispatch.
- Navigation.
- Application state.
- Error boundaries.
- Centralized workflow visualization.

## Server

Provides orchestration APIs including:

- `/plan`
- `/synthesize`

The server coordinates planning and synthesis operations.

## Distributed Execution

Connected machines independently execute assigned work while reporting state back to the shared system.

This allows multiple machines to operate concurrently while the user maintains a single view of the overall workflow.
